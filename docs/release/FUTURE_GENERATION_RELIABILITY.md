# Complete future generations and revisions

The reported revision saved a new image, but the planner returned Google 400 INVALID_ARGUMENT on the discovered stable Flash model. The diagnostic classified it as a generic request-argument rejection. The old job still became complete even though its plan was unavailable. No historical project is rewritten by this release.

Structured-output compatibility now handles a generic 400 by retrying without the provider's constrained schema, retaining both photos and the full JSON specification. Strict application validation still applies to the returned catalog, quantities, steps, checks and references. Temporary upstream/connection failures get one bounded retry under the same deadline; authorization, configuration and quota failures remain distinguishable and do not trigger uncontrolled model retries. Successful model discovery is cached per fetch implementation and API-key hash for five minutes, preserving discovered output limits and explicit model pins.

Each new revision clears inherited materials, steps, cost/time allowances, measurements and approvals before checkpointing the revised image. Its plan always uses the revised image and updated request. New generations carry generationVersion=complete-v2. If first-stage planning fails recoverably, the operation automatically retries only the saved image's plan within its remaining execution budget. A still-incomplete result remains image_saved with plan_pending instead of being marked complete. The mobile loading flow persists bounded plan-recovery IDs before sending free follow-up requests, polls after restart/lost responses, and opens the result only after a matching completed plan exists. Successful free follow-ups complete the parent job status. No second image, token or revision is generated for planning recovery. Provider outages or persistent invalid output end in an explicit incomplete state, never an invented or inherited plan.

Saved source/reference/material photos download concurrently. The mobile list batches private photo signing and caches URLs within an account, retains displayed projects during quiet refresh, discards stale loads, and requests lightweight job status instead of loading all job-result projects. No model-quality, plan-validation, safety, purchase, account or permission requirement is removed for speed.

Regression coverage includes generic format incompatibility with both images retained, reuse of discovered model/output caps, bounded transport retries, automatic revised-plan recovery, parent-plan isolation, pending-versus-complete status, follow-up completion, durable client retry IDs, lost responses/restarts, bounded/permanent failures, private image batching/cache expiry and account isolation. Physical-device acceptance and live provider results are separate from these deterministic checks and are recorded after deployment when available.

The explicitly enabled live release check passed against the actual production AI configuration, using the public OpenCV building sample and no customer data writes. A new two-planter design produced 7 materials and 10 phases in 71,987 ms; its plywood/paint revision produced 9 materials and 10 phases in 71,549 ms. Both images were valid, the revision image/materials/steps differed, every fixture material had a positive quantity and price, cost ranges were ordered, and every phase had actions/checks. This verifies those concrete generations rather than guaranteeing every possible AI result. The one-time build opt-in was removed afterward; ordinary builds never run these billable checks automatically. The live check does not exercise native navigation, billing or a real phone.
