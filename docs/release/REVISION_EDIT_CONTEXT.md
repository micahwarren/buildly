The old revision route reused the new-project request parser and merged client-supplied fields over the saved project. The image service received the current image, but its shared prompt also contained new-project instructions and attached the original site as another visual anchor. That implementation attempted an edit; it did not establish that a particular poor revision was caused by only one of these paths.

Revision requests now need only `{ id, change }`. The server resolves the owner-checked saved version, hydrates its current generated image, and retains its scope, details, dimensions and references. Extra fields from older clients cannot replace that context. Original request hashes remain stable for older retry keys, while durable revision payloads contain only the ID and change. Plan recovery still resumes its saved image without another image call.

The revision has its own image-edit prompt. The selected current design is the first editable photo; the original site is retained for the final visual audit and planning, rather than being attached to the image editor as a competing base. Inspiration/material images stay labeled as secondary preferences. The initial project request, current saved scope and accumulated revision instructions are carried explicitly, even if the interpreter produces a short summary. The latest request changes only its target; earlier unrelated requirements remain. Older snapshots recover the original scope through at most three owner-scoped parent lookups, without rewriting those snapshots.

The updated image, visual review, complete plan and final material audit receive the revision context. A missing saved design or scope fails before interpretation; there is no fallback to new-project generation. The existing two-candidate review bound, immutable version history, revision accounting, checkpoint and automatic plan-only recovery remain.
